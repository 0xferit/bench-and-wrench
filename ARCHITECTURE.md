# Collection architecture

## Catalog

Each tool has one authored entry in `tools/`. That entry owns the collection's assessment: purpose, reasons for inclusion, limits, relationship to the maintainer, and links to supporting work. The README is the entry point and index, not a second copy of those assessments. Every entry has the same four parts, an opening paragraph on the problem it solves, why it earns a place, when it is useful and its limits, so two entries can be read side by side; the build names those sections once and refuses an entry that lacks any of them, and the home page's account of how an entry reads, one row and one authored drawing (`site/illustrations/entry-*.svg`) per part, is built from the same list. Its use cases come from the entries too: every bullet under when an entry is useful becomes one numbered case tagged with its tool, shown beside that tool's authored drawing (`site/illustrations/usecase-*.svg`) with the drawing's focus group in the same position marked by the build, so a new bullet or entry needs no new markup; a tool without a drawing shows the spanner, and bullets beyond a drawing's focus groups show it unmarked.

The catalog uses Markdown so it remains readable directly in the repository. The website is generated from these entries rather than maintaining a competing catalog: the tool rows, the header's Tools dropdown and the footer's tool links all come from the same records.

## Upstream boundary

Tool implementations, releases, installation instructions, licenses, and support remain in their upstream repositories. This collection links to those authorities. It does not vendor tools or create separate release streams merely by featuring them.

An entry states whether its relationship is Built, meaning I author and maintain the tool, or Curated. A Built entry links to its source; a Curated entry claims neither authorship nor maintenance.

## Plugin marketplace

The repository is an installable marketplace for Claude Code and Codex. `.claude-plugin/marketplace.json` owns the marketplace identifier and plugin sources. External plugins are fetched directly from their upstream repositories at full commit hashes, keeping reviewed code stable until an explicit catalog update. Original packages can live inside this repository with relative sources. A catalog entry does not imply support for every host's runtime: Live Gantt still reads Claude Code sessions when its skills are installed in Codex.

`scripts/build_marketplace.py` derives `.agents/plugins/marketplace.json` from that catalog and the README title. The generated file adds Codex's display name and opt-in installation policy. It is tracked so a fresh clone works without a build step. Its check mode detects drift without rewriting files. The two host formats exist because Claude's catalog has no marketplace display-name field and Codex has its own presentation and installation-policy fields; their plugin identities and source pins have one authored definition.

## Website

The build in `scripts/build.py` reads the tool order from the README and the assessments from the linked catalog entries. It combines those records with the layout in `site/template.html` and emits the static site into `dist/`. Generated output is ignored by Git and can be recreated without installing dependencies.

The renderer supports the catalog's paragraphs, second-level sections, flat lists, and inline links, emphasis, and code. It escapes authored text and rejects executable link schemes before writing a page. It is deliberately a small catalog renderer rather than a general Markdown engine. Boundary checks exercise the command against temporary catalogs, including a new tool and invalid input.

`site/style.css` owns the design tokens: colour, type scale, spacing and motion curves. Every length is in `rem`, and the root size is a share of the viewport width with one value per breakpoint (desktop, 991px and below, 767px and below), so the whole sheet scales as one drawing and those three values are the only breakpoints. Its first `:root` block is the light palette, and a `prefers-color-scheme` block redefines the same colour tokens for dark mode. The build derives the light and dark browser theme colors and the favicon colors from those blocks. The mark, `site/assets/mark.svg`, takes its colours from the page's tokens when inlined and falls back to the light palette as a favicon, which cannot follow the viewer's theme. The PNG icons beside it (`site/assets/favicon-light-32.png`, `site/assets/favicon-dark-32.png`, `site/assets/favicon-48.png`, `site/assets/apple-touch-icon-180.png`, `site/assets/icon-192.png`, `site/assets/icon-512.png`) are rendered once from the mark in each palette and committed, because the build has no rasteriser; they must be re-rendered whenever the mark or the palette changes. Its parts carry ids and a unit path length, so the footer references each part for its hover facets and the page loader traces its outline, instead of either copying the geometry. The page is one ruled sheet inside a fixed frame: every module is a bordered cell, and cells are the only layout primitive. The margin outside the frame is a fixed paper-and-grain ring stacked above the header and content, so scrolled content is clipped at the frame line. The first screen is exactly one viewport on desktop and at least one below 992px, where it grows instead of shrinking the drawing below a floor, with a fixed header that hides on scroll, a ruler-framed drawing and a title row. The paper grain, `site/assets/paper-grain.png`, and the button dissolve mask, `site/assets/pixel-mask.svg`, are generated images owned by this repository. The ruler tick and plus masks, `site/assets/tick-h.svg`, `site/assets/tick-v.svg` and `site/assets/plus.svg`, and the approach cells' hover grid, `site/assets/grid-tile.svg`, are authored here too. Archivo (headlines, body) and Geist Mono (labels, indices, buttons) are self-hosted under `site/assets/fonts` with their Open Font License texts, so the page makes no third-party requests. The hero drawing, `site/illustrations/hero-spanner.svg`, is authored art drawn to a stated scale and inlined by the build. The plan drawing, `site/illustrations/bench-plan.svg`, is authored the same way; the build fills in the spanner from its one copy of that geometry, and the drawing keeps the reference plan's view box so offsets ported as CSS lengths keep their scale on screen. Its limit marks come from the catalog: every paragraph of an entry's limits becomes one numbered mark on the drawing and one callout. The drawing declares only where marks may go, its tool sheets as zones named by tool plus one default zone, and the build stacks each tool's marks in its zone and writes their view-box positions into the markup; so a new entry needs no change to the drawing, and the stylesheet places each marker button and callout from the view box rather than from measurement. The footer wordmark is SVG text in the self-hosted Archivo rather than outlined paths, so it follows the README title without a font tool in the build. Its layout is CSS (the `cap` unit places the lines), and the script draws the construction marks from the rendered glyphs' positions and ink edges, so neither holds a copy of the font's metrics. Each build empties `dist/` first so retired assets are never deployed. `DESIGN.md` is the design system's one document: principles, token roles, type, layout, components, motion, accessibility and how a tool adopts the system. The build renders it to `design-system.html` through the same page shell as the home page (`site/template.html` holds the shell, which closes every page with the call to action and footer, `site/home.html` the home content and `site/loader.html` the home page's opening sheet). Directives in the document pull facts from their owners instead of copying them: the colour table and scales come from `site/style.css`, and each component specimen is a file in `site/specimens` shown both live and as source. A contrast directive carries its own threshold, translucent colours are judged on the ground they sit on, and the build refuses to emit any page when a pair falls below its threshold in either palette, so the documented accessibility claims cannot drift from the tokens. The accent keeps the reference's exact vermilion, which is below 4.5:1 for small text; the two accent pairs carry a 3:1 threshold and say so in `DESIGN.md`. A test checks that every class a specimen uses exists in the stylesheet. Tools outside this repository adopt the system by copying the token blocks and fonts, as `DESIGN.md` describes; they do not import from the site. Illustrations are explicitly labeled examples, not live tool data. The small browser script only adds behaviour: opening sheet, smooth scrolling, reveals, cursor, pointer readout and guides on the hero drawing, scroll-driven statement and strip, field notes, footer wordmark, phone menu and button dissolve. It reads every geometry value a drawing declares from that drawing, and every colour and transition curve from the stylesheet's tokens, so the script holds no copy of them. Scroll-driven motion goes through one scene primitive in the script: a scene maps the scroll position between a start and an end, written as the reference's ScrollTrigger edge pairs, to progress (an edge that depends on the screen is a function the scene reads again on every update, so a resize across a breakpoint cannot leave it stale), and a timeline lays out tracks with its position grammar, so scenes ported from the reference keep their numbers. A scrubbed curve is evaluated per frame rather than by the browser, so the script owns those curves as named power eases. Scenes measure their trigger from the live layout on every update instead of caching positions, so a font load, an opened note or a resize cannot leave one stale; a scene therefore never moves its own trigger. Under reduced motion and while printing every scene shows its end state. A pinned scene is held by CSS sticky positioning inside a track whose height sets its length in viewports; the script never pins or sizes it, so without the script, under reduced motion and in print the track collapses to its content and the stage is a static cell. A scene's script writes only progress, live measurements and the state that progress selects, as custom properties and classes; the start values, offsets, units and durations of what it moves stay in the stylesheet. Selected state is a function of the scroll position alone, so scrolling either way or jumping to a point shows the same state there. A choice the reader makes inside a scene, such as an open limit, is not scroll state: it lasts until the reader closes it or the scroll crosses an edge of the part of the scene that shows it. A scene may close part of its stage, as the plan closes its side panel, only in the pinned layout and only by clipping it, so the same markup is open without the script, under reduced motion and in print. A scene may hold the reveal of content it uncovers and release it when that content opens. A pointer follower, such as the entry parts' accent rule, is not a scene: it reads the pointer and the live layout each frame only while its block is in view, settles and stops, and with no mouse in the window rests at the window's middle, so scrolling alone selects what it selects; it only chooses which of the labels already in the markup shows. An accordion such as the use cases is native `details` and `summary`, exclusive by name, so it opens by keyboard and without the script; the script only adds the slide and swaps the drawing beside it, which is decoration hidden from assistive technology. A scene hides layered content by fading it, never with `visibility` or `aria-hidden`, so everything a scene shows in turn stays in the accessibility tree and in the static layout. Without the script the page and its links still work, and every scene only decorates content that is complete in the markup. The opening sheet shows only on a page the head script has marked as scripted, and a stylesheet timeout hides it even if the script stalls, so it can never cover the page for good. There is no backend, authentication flow, analytics, or runtime connection to either featured tool.

## Hosting

Cloudflare Workers Static Assets serves the public deployment identified in the README. Only the generated `dist/` files are uploaded through the direct-upload interface. There is no Worker module, server process, secret, or runtime binding. Cloudflare owns hostname and routing configuration; HTML paths use automatic trailing-slash handling, and missing assets return a not-found response. These are static documents with fragment navigation, so an application-router fallback would hide broken links.

`site/robots.txt` owns the public crawl policy and is copied to the deployment root. It allows crawlers and explicitly permits search and use as input to artificial intelligence models, including agent browsing. All meaningful page content is server-rendered HTML, so a crawler does not need to execute JavaScript. Cloudflare's zone-level AI bot policies do not apply to this account's `workers.dev` hostname; no unrelated zone protections are changed.

The private ChatGPT Site identity and output directory remain in `.openai/hosting.json`. It is an independent preview snapshot, updated only when explicitly published to that service. Its source repository is a deployment copy, not a second authored collection. The GitHub catalog remains the working source for both hosts.
